THE QUESTION

Before asking whether a coding agent improved, it helps to know exactly what it was tested on. This project focuses on the infrastructure behind that question: task provenance, evaluation isolation, deterministic training schedules, and recoverable runs.

01

Knowing where each task came from

I developed source tracking and training-data preparation tools for repository tasks, alongside checks for overlap between development and evaluation data. These checks help prevent an apparent improvement from coming from exposure to the evaluation material.

02

Making runs comparable

Deterministic schedules, token accounting, and recovery checks make the conditions of a run explicit. Test-result validation adds another boundary: the evaluation needs to check the intended behavior and preserve enough information to inspect failures.

03

Separating infrastructure from performance

The project was developed around the Gemma developer-agent competition. The public repository documents implementation and readiness limits. Evaluation tooling and successful software tests do not, by themselves, demonstrate learned gains on unseen repository tasks.

INSIDE THE ENGINEERING

Make an improvement reproducible.

  1. 01

    Track the task’s lineage

    Repository tasks carry source provenance and evaluation contracts. Checks for overlap and quarantine keep questionable material out of the training path. This makes the boundary between development data and held-out evaluation something the tooling can inspect.

  2. 02

    Read the tests, not just the headline

    The JUnit audit preserves individual test-case outcomes and rejects contradictory aggregate counts. Failures, errors, and skipped cases remain distinct. A successful process exit or an attractive summary count cannot substitute for the underlying test evidence.

  3. 03

    Resume the same experiment

    Deterministic schedules and token accounting make training inputs and update boundaries explicit. Resume checks reconstruct the remaining schedule and reject corrupted counters, helping a recovered run continue the intended experiment rather than quietly becoming a different one.

These are implemented evaluation and training-preparation mechanisms. The repository does not yet establish learned gains on unseen repository tasks.
